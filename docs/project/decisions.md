Only the Next server's allowlisted identity (`writers` table, `SPACETIME_TOKEN`) can write; browsers subscribe anonymously and read. The server calls reducers over HTTP (serverless-friendly). Published to maincloud as database `geoswarm`. Backend is chosen by `LIVE_BACKEND` (default spacetime when configured, else convex, else SSE); the browser follows what `/api/agents` reports. We no longer claim the Convex track (one of Convex/Spacetime per team). Details: [web/README.md](../../web/README.md#spacetimedb-live-shared-mission-state-primary).

- **2026-10-24: Agent creation + library design** (agent-creation owner):
  - **"Marketplace" = one shared library**, no accounts/publishing; marketplace flavor only (creator, usage counts on cards).
  - **One `createAgent()` path** for both Hub prompt-to-create and mid-run spawns. A single structured-output Claude call (Opus) returns either `{reuse: <id>}` (library checked first) or a new config `{name, description, tools, dataSources, coverage, vehicle, color, prompt}` with id `custom-<slug>`.
  - **Generated agents run on a generic tool-use loop**: Claude Sonnet 5.5 with the agent's prompt as system prompt, only its allowed tools plus `emit_findings` (enforces the finding schema). Caps: ~6 turns, ~45s, ~15 findings; one `agent_log` line per tool call.
  - **v1 tool primitives**: Claude server-side `web_search` + `web_fetch`, our `http_get` (via `lib/http.ts`, http(s) only, private/loopback/link-local hosts blocked), and `geocode` (Nominatim, bounded to region bbox; fallback to region center at lower confidence; findings far outside the region dropped). As built, `geocode` is applied automatically to reported addresses rather than exposed as a model tool. No transcription. Keep `scrape` swappable for Bright Data.
  - **Spawn triggers**: planner gaps (already wired) + one post-sweep gap check in **Ask mode only** (max 1 per run). No worker-spawns-worker.
  - **No approval gate**: spawned agents run immediately, are temporary (server-side temp map, invisible to other runs' planners), and get **Keep / Discard** in the run panel after `run_done`. Kept agents join the library and the Ask planner's roster, not Insights `defaultAgents`.
  - **Library persistence**: JSON file (`web/data/agents.json`); migrate if a backend is chosen.
  - **Hub**: prompt → preview using `AgentCard` (name + prompt editable) → Save; Delete for custom agents.
  - **No API key**: spawning disabled, gaps shown as notes, Hub create disabled with "needs ANTHROPIC_API_KEY". No mocked agents.
  - **Rendering**: generated findings use `category = "custom"`, colored by the agent's color.
  - **Usage counts on cards** show how many orchestrator profiles include the agent in their Insights team (not per-run usage).
  - **Demo spawn**: Storefront Scout "good spot for a café?" → gap → spawned agent pulls SF restaurant health inspection scores (DataSF). Rehearse until reliable.

- **2026-10-25: Auto-routing replaces picking an orchestrator.** The picker defaults to **Auto**: the user just asks, and the planner call that already picks agents also picks the profile (`profileId` + a ≤12-word `routeReason` in its structured output), so there is no extra Claude round trip (planner latency unchanged in testing, ~6–7 s either way). Without Claude (no key, quota, planner error) a keyword router decides (`web/src/lib/orchestrator/route.ts`). Insights mode with Auto uses the Site Risk Analyst team. A new `routed` RunEvent records the choice; the run row keeps `profile_id = "auto"` until the SpacetimeDB/Convex `append_events` handler copies it from that event (module change in source, **needs `npm run spacetime:publish:cloud`**; until then the Missions list reads the routed events directly). Picking a specialist still forces it. Reason: one less decision before the demo's first question, and the routing itself shows the orchestrator reasoning.
- **2026-10-25: Bright Data + Apify integrated as live-data workers (both sponsor tracks).** The integration is four built-in workers plus one runtime change. **Bright Data:** Rent Scout (Web Unlocker → Craigslist apartment search, median rent + listing pins), Local Pulse (SERP API → Google + Reddit/Nextdoor threads), and the generated agents' `scrape` primitive, which becomes a client-side `fetch_page` through Web Unlocker when keys are set (falls back to Claude `web_fetch` without keys and to a direct fetch on error; `urlGuard` still applies). **Apify:** Review Radar (`compass/crawler-google-places`, polygon-restricted, ≤30 places, 20 s, $0.25 cap) and Hearing Watch, which runs our own Actor `web/apify/actors/sf-planning-notices` (SF Planning notices table + DataSF EAS geocoding) for Best Actor. Each worker is inert without its keys (`missingEnv()` in `web/src/lib/sponsors/keys.ts`; the worker logs "needs <KEY>"). There is no mock or fixture data at runtime; recorded HTML is used only in unit tests. Craigslist was chosen over Zillow/Apartments.com because its search page is public, `robots.txt` allows `/search`, and it carries coordinates (JSON-LD). The planner filters on `missingEnv()` (done in the agents entry below). Both Actors run with a 20 s timeout: with `apify.ts`'s 8 s HTTP margin that stays under the orchestrator's 30 s per-worker limit, so Apify ends a slow run itself instead of the orchestrator abandoning a call that is still being billed. Open: push the Actor and set `APIFY_PLANNING_ACTOR`.
